## 2. 계획과 달라진 판단과 이유

1. **P1·P2 를 화~목에서 화 하루로 압축.** 요일표는 P1(화~수), P2(목)였다. 실제로는 11-17 하루에 둘 다 끝났다. 이유는 무인 세션 한 번의 처리량이 설계서 가정보다 컸고 순수 함수·테스트 분리가 잘 되어서다. 부작용: 26파일 +1,455줄 한 커밋은 리뷰 단위로 너무 크다. 요일표 추정은 "일 2~3작업"으로 올려도 된다.
2. **남는 날 슬롯을 순서대로 소화(P3, B).** 설계서 의도 그대로다. 단 11-18 보고서가 "첫 `[ ]` 가 회고라 건너뛰었다"고 적었는데, 이 규칙은 PROGRESS 8.1 에 이미 쓰여 있어 문제는 없다.
3. **11-19 에 W49 W1·W2 를 집음.** 11-18 사용자 지시(위키백과 기능 전수조사)로 W49 큐가 등록됐고, W48 의 남는 날 ③~⑥ 을 W49 큐 뒤로 옮겼기 때문에 첫 `[ ]` 가 W49 W1 이 됐다. 판단은 규칙대로이나 **C 알림(W45 부터 4주째 미착수)·`useOptimistic`·S·K 가 계속 뒤로 밀렸다**. 사용자 신규 지시가 이미 큐의 앞을 먼저 차지하는 패턴이 W47(분류 트리)에 이어 두 번째다.
4. **"build 미확인" 규칙을 모든 `[x]` 에 붙이고 원인을 더 파지 않음.** 설계서 3절·W49 6절 지침이다. 올바르다. 대신 `[x]` 의 의미가 "컴파일·타입·단위 테스트까지"로 굳었고 화면은 한 번도 실제 데이터로 그려지지 않았다.
5. **`?rev=` 분기에 `httpUrl` 재검증을 같은 날 추가(656c218).** 옛 스냅샷의 위험 URL 이 `next/image`·`<a>` 로 들어갈 수 있다는 자체 보안 검토의 결과다. 설계서에 없던 보완을 세션이 스스로 넣었다. 좋은 판단이다. 스냅샷에 저장된 다른 URL 필드가 더 있는지는 확인하지 않았다.
6. **한도기 정리를 "10,000개 초과 시"에서 "창마다 한 번"으로 변경(M2).** 설계 테스트(3 IP → 창 뒤 size 1)를 만족하려는 선택이다. 메모리 상한이 최근 2창의 IP 수가 되므로 저트래픽에서는 문제없다.
7. **탭 줄을 분류 갤러리에서만 보이게 변경(P1).** 상황 갤러리는 문서를 갖지 않아 항상 빈 화면이었다는 이유이고 ADR 0002 와도 일치한다. 되돌리는 방법이 보고서에 적혀 있다.
8. **`MarkdownEditor` 대신 `textarea`(P1).** 위키 템플릿 버튼이 게시판에 맞지 않는다는 이유다. 후속 필요 여부는 미정.
