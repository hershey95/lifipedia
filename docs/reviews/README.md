# 교차 리뷰 & 주간 보고

Claude 와 Gemini 가 서로의 결과물을 리뷰하고, 주말 회고·계획에 반영한 뒤 **사용자에게 보고**하는 절차.
에이전트끼리는 직접 대화하지 못하므로 이 폴더의 파일이 유일한 소통 창구다.

## 흐름

```
Gemini 콘텐츠 ──► Claude 리뷰 ─┐
Claude 코드   ──► Gemini 리뷰 ─┤──► docs/reviews/*.md ──► (주말) Opus 회고·계획 ──► BACKLOG.md
                               │                                  │
                               └──────────────────────────────────▼
                                          weekly-<YYYY>-W<주차>.md 작성 → 사용자 보고 → 승인 후에만 반영
```

## 소통 프로토콜 (사용자 중계 없음)

에이전트끼리 직접 호출은 못 하므로 **파일 우편함**으로 주고받는다. 사용자는 중계하지 않고, 각 에이전트는 세션을 시작할 때 자기 우편함부터 확인한다.

| 방향 | 위치 | 전달 방법 |
|---|---|---|
| Claude → Gemini | `docs/reviews/inbox/gemini/<날짜>-<주제>.md` (`상태: 열림`) | Claude 가 `claude/peaceful-pasteur-abbqgx` 로 push → Gemini 가 `git fetch` + merge |
| Gemini → Claude | `docs/reviews/inbox/claude/<요청과 같은 이름>-reply.md` + 콘텐츠 커밋 | Gemini 는 로컬 커밋까지만. Claude 가 같은 Mac 의 `/Users/macmini/Lifipedia` 를 직접 읽어 확인 |
| 승인 후 반영 | Gemini 의 `content/...` 브랜치 | Claude 가 재검수 후 push (Gemini 는 push 권한 없음) |

### 주간 일정 (요일별 작업) — 한 주는 **일요일에 시작**해 토요일에 끝난다

Opus 사용량이 한 요일에 몰려 주중 작업이 막히지 않도록, 설계서를 일요일에 작성한다.

| 요일 | Claude | Gemini |
|---|---|---|
| 일 | **Opus**: ① 지난주 Gemini 콘텐츠 피드백(리뷰 종합 + 다음 주 콘텐츠 지침) ② 승인된 계획으로 이번 주 큰 기능 **설계서**(`docs/design/<연도>-W<주차>-<기능>.md`) 작성. 주간 갤러리 목록·요일별 계획을 `inbox/gemini/` 에 기록 | 콘텐츠 (계획에 지정된 갤러리) + 지난주 Claude 피드백 반영 |
| 월 | 09:00 **Gemini 의 설계서 리뷰를 수용/거절 판단** → 설계서 확정(Sonnet, 큰 이견만 Opus) → 기능 구현 시작 | 06:00 **설계서 리뷰**(Claude 결과물 리뷰 ①) + 콘텐츠 |
| 화 | 09:00 전날 Gemini 코드 리뷰 수용 판단 후 반영 → 기능 구현 | 06:00 전날 Claude diff 리뷰(②) + 콘텐츠 |
| 수 | 09:00 수용 판단·반영 → 기능 구현 + 통합 | 06:00 전날 diff 리뷰 + 콘텐츠 |
| 목 | 09:00 수용 판단·반영 → 통합·`typecheck`/`test`·정리, 반영 마감 | 06:00 전날 diff 리뷰 + 콘텐츠 |
| 금 | **Opus**: 주간 회고. 양방향 피드백의 수용/거절 결과 점검, 이견 판정 | 벤치마크: 위키피디아·나무위키 + 이번 주 Claude 결과 **총평 리뷰**(③) |
| 토 | **Opus**: 갭 분석, `BACKLOG.md`, 주간 보고 작성 → **사용자 승인 대기** | 벤치마크: 레딧·디시인사이드 |

- 토요일 보고를 사용자가 승인해야 일요일 설계서 작업을 시작한다. 승인 전에는 새 주 작업을 시작하지 않는다.
- Gemini 의 일~목 콘텐츠는 일요일 계획 파일이 지정한 갤러리를 하루 1곳씩 처리한다. 계획에 없는 날은 사용자 승인을 기다린다.
- Opus 는 금·토·일 연속 3일 사용되므로, 사용량이 부족하면 설계서(일) 또는 회고(금)를 Sonnet 으로 낮추고 그 사실을 주간 보고에 기록한다.

### Gemini → Claude 피드백과 수용 규칙

- **리뷰 대상**: ① 월요일 설계서 ② 화~목 전날 코드 diff ③ 금요일 이번 주 총평. 범위는 하루치로 제한하고 템플릿(문제/근거/심각도/제안)과 "지적 3개 이상 또는 확인 항목 나열" 규칙을 똑같이 적용한다.
- **위치**: Gemini 는 `docs/reviews/inbox/claude/<날짜>-gemini-on-claude.md` 에 쓰고 로컬 커밋한다.
- **수용 판단**: Claude 는 항목마다 **수용 / 부분 수용 / 거절 + 이유**를 `docs/reviews/inbox/gemini/<날짜>-feedback-response.md` 에 기록하고 push 한다. 맞장구로 전부 수용하지 않고, 근거가 부실한 지적은 이유를 달아 거절한다.
- **반영 순서**: 리뷰 → 수용 판단 기록 → (수용 항목만) 반영 → 테스트 통과. 큰 변경(스키마, 서비스 철학, 우선순위)은 반영하지 않고 사용자 결정 사항으로 올린다.
- **이견**: 금요일 Opus 가 판정한다. 철학 위반 지적은 최우선 검토.
- **Gemini 리뷰 품질**: 첫 주는 오탐률과 근거 유무를 기록해 두고, 부실하면 사용자에게 Gemini 리뷰 축소를 제안한다.

### 상호 피드백 시퀀스와 정성 평가
매일 `scripts/daily-dispatch.sh` 가 Gemini 를 부르고, 무인 Sonnet 세션이 **사실 대조 + 정성 평가**(서비스 적합·서술 품질·정보 완결성·일관성·위험)를 하고, 서로 피드백→수용/거절→반영을 이어 간다. 순서와 파일 위치는 `docs/reviews/RELAY.md` 의 "정성 평가", "상호 피드백 시퀀스" 참고. 운영 원칙은 **선조치 후보고**: 사용자 승인을 기다리지 않고 판단·조치하며, 방향 변경·반복 실패·위험·사용자 결정이 필요한 것만 보고한다.

### 매일 공통 루틴 (스케줄 기반, 시각은 KST 기본값이며 조정 가능)

| 시각 | 누가 | 하는 일 |
|---|---|---|
| 06:00 | Gemini (예약 실행) | `git fetch` + merge → 우편함(`inbox/gemini/`)의 열린 요청과 오늘 계획을 읽고 작업 → `content/` 로컬 커밋 → 답신 파일 작성 |
| 09:00 | Claude (예약 실행) | `/Users/macmini/Lifipedia` 의 새 커밋과 답신 확인 → 샘플 검수 → **통과하면 content 브랜치 push**, 미흡하면 수정 요청을 `inbox/gemini/` 에 써서 push |
| 작업 종료 시 | Claude | 코드·문서 push 시 변경 요약, 피드백, **내일 Gemini 가 할 일**(`inbox/gemini/<날짜>-plan.md`)을 같이 담는다 |
| 다음날 06:00 | Gemini | 위 내용을 pull 해서 반복 |

- Claude 의 push 범위: `claude/peaceful-pasteur-abbqgx` 와 검수 통과한 `content/*` 브랜치만. `main` 이나 force push 는 금지. 코드는 `typecheck`·`test` 통과 후에만 push.
- Gemini 는 push 하지 않는다. 로컬 저장만 하고, 반영은 Claude 의 검수 뒤에 이뤄진다.
- 금·토: Gemini 가 벤치마크 조사, 금요일에 Opus 회고, 토요일에 갭 분석과 주간 보고(이 파일 아래 템플릿)를 작성하고 사용자 승인을 기다린다.

- 요청은 처리 후 Claude 가 `상태: 완료` 로 바꾼다. 답신이 없으면 미처리로 본다.
- Gemini 의 "완료" 보고는 그대로 믿지 않는다. Claude 가 로컬 커밋과 `git ls-remote` 로 직접 확인한다.
- Gemini 의 시작 지침은 루트의 `GEMINI.md` (자동 읽힘 여부는 첫 사용에서 확인).

## 규칙

1. **형식 고정**: 리뷰는 아래 템플릿의 표로만 쓴다. 자유 서술·장문 금지.
2. **범위 제한**: 하루치 변경분만 본다. 콘텐츠는 아이템 2~3개 샘플, 코드는 그날의 diff. 전체를 훑지 않는다.
3. **맞장구 금지**: 지적을 최소 3개 쓴다. 정말 없으면 "확인한 항목"을 구체적으로 나열한다(예: 가격 3건 출처 직접 확인). "문제 없음"만 쓰는 리뷰는 무효.
4. **자동 반영 금지**: 리뷰는 의견일 뿐이다. 리뷰 → BACKLOG → 사용자 승인 → 반영 순서를 지킨다. 상대 결과물을 리뷰어가 직접 고치지 않는다.
5. **이견 처리**: 작성자와 리뷰어 의견이 갈리면 주말에 Opus 가 판정한다. 방향이 갈리는 큰 사안(스키마, 서비스 철학, 우선순위)은 판정하지 않고 사용자 결정 사항으로 올린다.
6. **Gemini 역량 관찰**: 첫 주는 Gemini 리뷰의 품질(근거 유무, 오탐률)을 기록한다. 부실하면 Claude 단독 리뷰로 전환할지 사용자에게 제안한다.
7. **서비스 철학 우선**: 운영자 큐레이션 금지(투표·점수를 임의로 만들지 않음) 원칙에 어긋나는 제안은 철학 위반으로 표시하고 채택하지 않는다.

## 주간 보고 템플릿 (주말 회고·계획 완료 후 사용자에게)

주말 회고·계획을 마친 에이전트(Opus)는 `docs/reviews/weekly-<YYYY>-W<주차>.md` 를 쓰고,
같은 내용을 요약해 **세션에서 사용자에게 직접 보고**한다. 사용자 승인 전에는 다음 주 작업을 시작하지 않는다.

```markdown
# 주간 보고 <YYYY>-W<주차>

## 1. 이번 주 한 일
- 기능(Claude): 
- 콘텐츠(Gemini): 갤러리 N곳, 아이템 M개

## 2. 교차 리뷰 요약
- 합의된 지적: 
- 이견과 Opus 판정: 
- 사용자 결정이 필요한 이견: 
- Gemini 리뷰 품질 관찰(첫 주): 

## 3. 벤치마크 갭 (위키피디아·나무위키·레딧·디시)
| 기능 | 출처 | 현황 | 철학 부합 | 규모 | 우선순위 |
|---|---|---|---|---|---|

## 4. 다음 주 계획안
| 요일 | 담당 | 작업 | 근거(리뷰/벤치마크) |
|---|---|---|---|

## 5. 사용량 메모
- 주요 소모 작업과 다음 주 조정안

## 6. 사용자 결정 필요 사항
```
