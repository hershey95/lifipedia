## 1. 지적 및 제안 사항

| # | 문제 | 근거 | 심각도 | 제안 |
|---|---|---|---|---|
| 1 | **활동 병합(Activity Merge) 시 문서 생성 건이 2중 중복 노출되는 결함** | `src/app/api/items/route.ts` (L82~91)에서 문서 생성 시 `Item.createdById = user.id`뿐만 아니라 `EditHistory(editorId: user.id, revision: 1, summary: '문서 생성')`도 동시에 생성함. 설계서 4절처럼 `Item(createdById)` 30건과 `EditHistory(editorId)` 30건을 단순 병합하면 모든 최초 문서 생성이 2건으로 중복 표기됨. | **높음** | `EditHistory` 쿼리 시 `where: { revision: { gt: 1 } }` 조건을 추가하여 순수 '편집' 건만 가져오거나, 아이템 생성과 편집을 단일 식별자(`itemId + createdAt`)로 디둡(deduplicate)할 것. |
| 2 | **Next.js App Router 캐싱에 의한 타인 개인정보 노출 위험** | 설계서 3절에 `robots: noindex`만 명시되어 있고 Next.js 동적 렌더링 보장 지침이 없음. `/me`는 세션 종속 개인 페이지이므로 정적 캐싱이나 공유 CDN 캐시(Edge Cache)에 걸리면 A 사용자의 마이페이지(Karma, 투표 내역, 프로필)가 B 사용자에게 노출될 위험이 있음. | **높음** | `/me` 페이지에 `export const dynamic = 'force-dynamic'` 필수 선언 및 HTTP 응답 헤더 `Cache-Control: private, no-store` 적용을 설계서 수용 기준에 명시할 것. |
| 3 | **정지 사용자(`isSuspended`)의 `/me` 진입 시 상태 안내 및 UI 비활성화 누락** | 설계서 4절에는 `PATCH /api/me` 시 403 거부만 기술되어 있고, `/me` 페이지(RSC) 진입 시의 정지 사용자 처리가 없음. 정지된 사용자가 화면상 정상 계정처럼 보이다가 수정 시에만 403 에러 팝업을 보게 되면 UX 혼란이 발생함. | **중간** | `isSuspended(user)`인 경우 `/me` 상단에 명확한 제재 안내 배너(`suspensionReason`, `suspendedUntil`)를 띄우고, 프로필 수정 폼(`input`, `button`)을 `disabled` 처리할 것. |
| 4 | **제재/삭제된 아이템(`isRemoved: true`)에 대한 고아(Dangling) 링크 발생 위험** | 규정 위반으로 삭제/블라인드된 아이템(`isRemoved === true`)에 대한 필터링이 누락되면 마이페이지 활동/투표 목록에 유해 문서가 그대로 노출되고, 링크 클릭 시 404 에러를 유발함 (`src/app/u/[id]/page.tsx` L21에서는 `where: { isRemoved: false }`로 이미 필터링 중). | **중간** | 활동 및 투표 쿼리 시 `item: { isRemoved: false }` 조건을 명시하고, 연관 문서가 삭제된 경우 "(삭제된 문서입니다)" 플레이스홀더 표시 및 링크 비활성화 처리를 추가할 것. |
| 5 | **프로필 수정 후 공개 프로필(`/u/[id]`) 캐시 무효화 누락 및 trim 검증 순서** | `PATCH /api/me` 성공 후 Next.js 캐시 무효화가 없으면 공개 프로필 `/u/[id]`에 이전 이름/소개가 남아 있는 stale 상태 발생. 또한 공백 문자열(`"   "`) 전송 시 trim 검증 순서가 모호함. | **낮음** | `PATCH /api/me` 성공 시 `revalidatePath('/me')` 및 `revalidatePath('/u/' + user.id)` 호출을 추가하고, zod 스키마를 `z.string().trim().min(1).max(30)`으로 정의하여 trim 후 길이 검증을 보장할 것. |

## 3. 결정 사항(D1~D4)에 대한 의견

| # | 결정 사항 | Gemini 의견 | 상세 이유 |
|---|---|---|---|
| **D1** | 투표·댓글은 기여에 넣지 않는다 | **수용 (전적 찬성)** | 투표/댓글을 기여에 포함하면 자가 투표 가중치 증폭 루프가 생기고, 봇이나 다계정 매크로로 의미 없는 댓글을 도배해 등급(STEWARD)을 올리는 어뷰징 비용이 지나치게 낮아짐. 현재처럼 문서 생성·편집만 기여로 인정하는 것이 서비스 신뢰성에 필수적임. |
| **D2** | 기여 로그 테이블을 만들지 않는다 | **조건부 수용 (보완 필요)** | 단기 마이그레이션 위험 회피 관점에서는 기존 테이블 활용이 타당함. 다만 지적 1에서 언급했듯 `Item(createdById)`와 `EditHistory(editorId)`의 중복(revision 1) 제거가 쿼리 레벨에서 반드시 처리되어야 함. 장기적으로는 롤백/문서 삭제 시 이력 보존을 위한 이벤트 로그 도입을 백로그로 남겨둘 것을 권장함. |
| **D3** | `/me` 와 `/u/[id]` 를 분리한다 | **수용 (전적 찬성)** | 공개 프로필(타인 열람용 위키 활동 요약)과 비공개 대시보드(본인 투표 내역, 프로필 수정, Karma 진행도)의 성격과 권한이 명확히 다름. 단일 라우트에서 조건부 분기를 할 경우 권한 검사 실수로 인한 개인정보 유출 사고 위험이 커지므로 라우트 분리가 적절함. |
| **D4** | 내 투표 내역은 본인만 본다 | **수용 (전적 찬성)** | 투표 내역이 타인에게 공개되면 특정 제품 지지/비토에 따른 사용자 간 낙인찍기, 보복성 다운보트, 집단 괴롭힘이 발생할 수 있음. 비밀투표와 투표 프라이버시 보장은 객관적인 위키 랭킹 형성에 핵심 요소임. |

## 4. 필수 3대 관점 분석

### (a) 실패 시나리오 (Failure Scenarios)
- **정지 사용자 접근**: 정지된 사용자가 `/me`에 진입할 경우 단순 403 차단보다는 정지 사유와 기간을 명확히 고지하고, 수정 동작만 비활성화하는 UX가 필요함.
- **삭제/제재 문서 참조**: 사용자가 과거에 작성/편집/투표한 아이템이 모더레이션 제재로 삭제(`isRemoved = true`)된 경우, 목록에서 제외하거나 삭제 상태임을 명시하여 404 링크 이동을 방지해야 함.
- **세션 만료**: 마이페이지를 띄워둔 상태에서 세션이 만료된 후 프로필 수정을 시도할 경우, 401 반환 시 클라이언트가 로그인 페이지(`/signin?callbackUrl=/me`)로 자연스럽게 이동하도록 처리해야 함.

### (b) 권한·프라이버시 (Auth & Privacy)
- **RSC 캐시 격리**: Next.js App Router의 캐시가 사용자 세션을 넘어 공유되지 않도록 `export const dynamic = 'force-dynamic'` 및 `private, no-store` 캐시 헤더를 강제해야 함.
- **타인 데이터 유출 방지 (IDOR 방지)**: 내 활동 및 투표 쿼리는 클라이언트 파라미터(`?userId=...`)를 절대 신뢰하지 않고 오직 서버 세션의 `currentUser().id`로만 제한 조회해야 함.

### (c) 멱등성 및 무결성 (Idempotency & Integrity)
- **프로필 수정 멱등성**: `PATCH /api/me`는 동일한 요청이 여러 번 호출되어도 최종 결과가 동일하므로 멱등함. 클라이언트 차원에서는 중복 제출 방지(`isSubmitting` 버튼 비활성화)를 적용해야 함.
- **활동 목록 정합성**: 단순 `take: 30` 병합 시 발생하는 최초 리비전 중복(revision 1)을 제거하여 활동 카운트 및 목록의 일관성을 보장해야 함.
