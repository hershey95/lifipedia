# 오픈소스 리서치: 가격 비교·추적 (2026-11-18)

범위: 가격 이력·그래프, 판매처별 수집, 변동 알림, 품절 감지, 한국 쇼핑몰 대응, 이상치 필터.
방법: `gh search repos` / `gh repo view` / `gh api` 로 별·라이선스·최근 push 를 직접 확인하고, `gh api` 로 README 와 핵심 소스를 읽었다(WebFetch 대신. 같은 원문). `docs/research/` 에 이전 파일은 없어 건너뛴 후보는 없다.
확인 못 한 것은 '미확인'으로 적었다. 코드(src/ prisma/ scripts/)는 수정하지 않았다.

## 우리 쪽 현황 (비교 기준)
- `Item.priceKrw Int?` 는 사용자가 입력한 대표가 한 값이다. 스키마 주석에 "크롤링은 MVP 범위 밖" 이라고 적혀 있다 (`prisma/schema.prisma:214-215`).
- 가격 이력 전용 테이블은 없다. 가격 변경은 `EditHistory.snapshot` 에 전체 필드로 남는다 (`prisma/schema.prisma:250-272`).
- 가격대 검증은 `src/lib/tier.ts` 의 `validateTierAgainstPeers` 다. 같은 테마 안 가격 3분위로 상대 판정하고, 표본이 6개 미만이면 통과시킨다.
- 구매 링크는 `Item.purchaseLinks Json [{label,url}]` 이다.
- `content-check.ts` 는 가격 '원' 숫자를 인용문과 대조한다.
- 철학상 제약: 운영자 큐레이션 없음, 신뢰도는 기여에서만, 재현 가능한 랭킹. 조회수는 순위 점수에 넣지 않는다(ADR 0001). 외부 크롤링으로 가격을 자동 갱신하면 "출처 불명의 숫자가 문서를 덮어쓰는" 문제가 생겨 철학과 부딪친다.

## (2) 우리에게 적용할 아이디어

### 아이디어 1. 가격 문자열 → 숫자 변환을 한 함수로 모으고, 모호하면 추측하지 않고 거절한다
- 무엇을: 사람이 입력한 가격 텍스트("1,299,000원", "129만 9천", "정가 150,000 → 129,000")를 `priceKrw` 정수로 바꾸는 단일 파서를 만든다. 서로 다른 금액이 둘 이상이면 첫 값을 고르지 않고 "금액이 여러 개입니다" 오류를 낸다.
- 출처: `changedetectionio/processors/restock_diff/filtered_price.py` (독스트링에 "taking the first would silently track the 'was' price" 라고 명시)와 `restock_diff/__init__.py` 의 `Restock.parse_currency` ("The one place price text becomes a number"). 둘 다 https://github.com/dgtlmoon/changedetection.io 에서 직접 읽었다.
- 우리 코드의 어디에: 새 순수 함수 `src/lib/price-parse.ts`(`parsePriceKrw(text): {ok, amount} | {ok:false, reason}`). 호출처는 `src/components/ItemForm.tsx`, `src/app/api/items/route.ts`, `src/lib/content-check.ts` 의 `FIG` 정규식 쪽이다. 지금 `content-check.ts` 는 정규식으로만 금액을 본다.
- 규모: S
- 철학 충돌: 없음. 규칙이 공개되고 결과가 결정적이다. 파서는 사용자가 쓴 값을 해석할 뿐 운영자가 값을 정하지 않는다.
- 참고: 한국 원화는 소수점이 없고 "만/천" 단위 표기가 있어 changedetection 의 로케일 처리(`price_parser`, babel)는 그대로 못 쓴다. 설계 아이디어만 가져온다. 전체 로직이 읽은 파일에 다 있는지는 확인하지 못했다(`gh api` 로 head 150줄 / 120줄만 읽음).

### 아이디어 2. 가격 이력은 별도 테이블 없이 `EditHistory.snapshot` 에서 뽑아 "가격 변경 이력" 으로 보여준다
- 무엇을: 문서 상세에 "가격 변경 이력" 표(날짜·값·편집자)를 추가한다. 가격이 바뀐 리비전만 골라 시계열을 만든다. 이전값 대비 변화율(%)을 같이 표시한다(changedetection 의 `get_price_change_percent`: `(price - prev) / prev * 100`, 소수 1자리, 변화 없음/이전값 0 이면 `None`).
- 출처: `restock_diff/__init__.py` 의 `Restock.get_price_change_percent` 와 `last_price` 필드, `restock_diff/plugins/default_charts.py` / `templates/restock_diff/chart_default.html` / `static/js/restock-price-graph.js` (차트를 서버 데이터로 브라우저에서 그림. JS 파일 본문은 읽지 않았고 존재와 역할만 확인).
- 우리 코드의 어디에: 새 순수 함수 `src/lib/price-history.ts` (`EditHistory` 행 → `{revision, at, priceKrw, changePct, editorId}[]`, 가격이 이전 리비전과 같으면 건너뜀). 화면은 `src/app/theme/[slug]/item/[itemSlug]/page.tsx` 의 기존 "최근 변경" 섹션 옆. 되돌려진 편집은 `EditHistory.revertOfRevision` 으로 걸러 낸다. 스키마 변경 없음(`db:push` 불필요).
- 규모: S~M (표만이면 S, 그래프까지면 M. 그래프는 SVG 직접 그리기로 의존성 없이 가능, 단 이번에 구현을 검증하지는 않았다)
- 철학 충돌: 없음. 이력의 출처는 기여자의 편집뿐이고 그 편집자가 표시된다(신뢰도는 기여에서만). 재현 가능하다(같은 `EditHistory` 에서 항상 같은 결과).
- 주의: `EditHistory.snapshot` 이 `priceKrw` 를 항상 담는지는 `src/lib/wiki.ts` 의 `EDITABLE_FIELDS` 에 `priceKrw` 가 있는 것으로만 확인했다. 기존 행 전체를 검증하지는 않았다(미확인).

### 아이디어 3. 가격 편집의 이상치 경고를 "같은 문서의 직전 값"까지 넓힌다
- 무엇을: 지금 `validateTierAgainstPeers` 는 같은 테마 동료 분포만 본다. 여기에 "직전 리비전 대비 변화율이 큰 편집(예: ±50% 이상, 임계값은 공개 상수)"이면 편집 폼에서 한 번 더 확인을 받는 규칙을 더한다. 기본적으로 막지 않고 확인만 요구한다.
- 출처: `restock_diff/forms.py` 의 `price_change_threshold_percent`("Threshold (%) for price changes since the previous check"), `price_change_min` / `price_change_max`. 원문에서 필드 이름과 라벨만 확인했고 동작 코드는 읽지 않았다.
- 우리 코드의 어디에: `src/lib/tier.ts` 옆에 `validatePriceJump(prev, next)` 순수 함수를 추가하고 `src/app/api/items/[id]/edit/route.ts` 에서 호출한다. 기여 규칙(`src/lib/contribution-rules.ts`)의 `SUBSTANTIVE` 에 `priceKrw` 가 이미 있어, 되돌려진 이상치 편집은 기존 원장 로직이 적립에서 제외한다.
- 규모: S
- 철학 충돌: 낮음. 임계값을 공개 상수로 두고 확인만 요구하며 운영자가 개별 판단으로 값을 지우지 않는다. 임계값이 곧 운영자 취향이 되지 않도록 `how-ranking-works` 에 근거를 적는 것이 좋다.

### 아이디어 4. "여러 후보 중 하나를 사람이 고른다" 구조를 구매 링크 가격 입력에 적용한다 (설계만 참고)
- 무엇을: 판매처별 가격을 문서에 넣고 싶을 때, 자동 수집값을 정답으로 덮어쓰지 않는다. 기여자가 "링크별 관측 가격 + 관측일 + 출처 한 줄"을 입력하게 하고, 같은 판매처에서 값이 갈리면 모두 보여준 뒤 기여자가 확정하게 한다. PriceGhost 는 JSON-LD·사이트별·CSS·AI 네 방법의 후보를 신뢰도 점수와 함께 보여주고 사용자가 최종 선택하게 한다.
- 출처: https://github.com/clucraft/PriceGhost README ("You Choose the Price. Always.", "Price Voting Modal"). 소스 코드는 읽지 못했다. 라이선스 미확인이므로 **설계 아이디어만** 참고한다.
- 우리 코드의 어디에: `Item.purchaseLinks` 의 JSON 모양에 `observedPriceKrw`, `observedAt` 선택 필드를 추가하는 안. `src/components/ItemForm.tsx` 입력, `src/lib/content-check.ts` 검증. JSON 필드 확장이라 스키마 변경은 없지만 `EDITABLE_FIELDS` 리비전 대상이라 편집 이력이 남는다.
- 규모: M
- 철학 충돌: 중간. 관측 가격은 시간이 지나면 낡는다. "관측일" 을 숨기면 거짓 정보가 되므로 반드시 날짜와 함께 보여줘야 한다. 자동 수집은 도입하지 않는다(아래 3절).

### 아이디어 5. "품절/재입고" 는 가격과 분리된 문서 상태로 둔다 (후순위)
- 무엇을: changedetection 은 `in_stock_processing`(재입고 감지 라디오)과 가격 추적을 독립 설정으로 둔다. 우리도 문서에 "단종/품절 제보" 같은 상태를 가격과 별개로 기여받을 수 있다.
- 출처: `restock_diff/forms.py` 의 `in_stock_processing`, `follow_price_changes` (둘 다 별도 필드). 동작 코드는 읽지 않았다.
- 우리 코드의 어디에: 신고 흐름(`Report`) 재사용. 신규 모델이 필요해 W45-4 신고 처리·제재(검토자 결정 대기)와 겹친다.
- 규모: M
- 철학 충돌: 낮음. 단 자동 감지 없이 사용자 제보만 쓴다. 지금은 **보류**를 권한다(PROGRESS 의 W45-4 가 막혀 있음).

## (3) 채택하지 않을 것과 이유
1. **판매처 자동 크롤링·스크레이핑 전반**(다나와·네이버쇼핑·쿠팡 포함): 이유는 세 가지다.
   - 철학: 외부 숫자가 문서를 자동 갱신하면 "신뢰도는 기여에서만" 이 깨진다. 값의 책임자가 없다.
   - 법적·운영 위험: 쿠팡·네이버 쇼핑은 약관상 자동 수집 금지일 가능성이 높다. 이번에 약관 원문은 확인하지 못했다(미확인). 공식 API 가 있다면 검토하되 이번엔 조사하지 않았다.
   - 생태계: 쓸 만한 한국 쇼핑몰 오픈소스가 없다(1절). `sammy310/Danawa-Crawler` 는 Selenium + 고정 `chromedriver` 바이너리 + GitHub Actions 일 1회 방식이라 NAS 배포(`docker-compose`)에 얹기엔 무겁다. 스키마 주석("크롤링은 MVP 범위 밖")과도 맞다.
2. **changedetection.io 연동·임베드**: Apache-2.0 이라 법적으로 가능하지만 Python 서비스를 별도로 돌려야 한다. 우리 스택(Next.js + SQLite 단일 컨테이너)에 비해 운영 부담이 크다. 필요한 건 가격 파싱 규칙과 변화율 계산 몇 줄이라 아이디어만 쓴다.
3. **AI 가격 추출·검증**(PriceGhost 의 Claude/GPT/Ollama 중재): 결과가 비결정적이라 "재현 가능한 랭킹" 원칙과 충돌한다. 외부 API 비용·키도 생긴다.
4. **변동 알림 푸시**(텔레그램·디스코드·Pushover): 현재 W48 의 "알림 3종"(C) 범위에 가격 변동은 없다. 가격이 자동 갱신되지 않으면 알림할 사건도 드물다. 이력 화면(아이디어 2)이 먼저다.
5. **사용자별 목표가 알림**(Discount-Bandit·PriceGhost 의 target price): 실시간 가격이 있어야 의미가 있다. 우리에겐 대표가 한 값이라 전제가 성립하지 않는다.
6. **다중 판매처 최저가 랭킹**: 가격을 순위 점수에 넣는 일이므로 ADR 0001 정신("순위는 투표·기여로만")과 충돌한다. 가격대(티어)는 분류용일 뿐이다.

## 우선순위 제안
1. 아이디어 1(가격 파서) → 2(가격 변경 이력 표) → 3(변동폭 확인) 순으로 모두 S~M 이고 스키마 변경이 없다. `db:push` 대기와 무관하게 진행할 수 있다.
2. 아이디어 4·5 는 설계 결정(관측일 표기, 신고 흐름)이 선행돼 사람의 판단이 필요하다.
3. 자동 수집은 이번에도 도입하지 않는다. 한국 쇼핑몰 공식 API·약관 조사가 선행돼야 한다(미확인).

## 이번 조사의 한계
- changedetection.io 는 `filtered_price.py`, `processor.py`(앞 260줄), `__init__.py`(앞 120줄), `default_charts.py`, `forms.py`(grep 한 줄들)만 읽었다. 그래프 JS 와 알림 로직 본문은 읽지 않았다.
- PriceGhost·Discount-Bandit·Danawa-Crawler 는 README 와 파일 목록만 읽었고 소스 파일은 읽지 않았다.
- 쿠팡·네이버쇼핑·다나와의 약관·공식 API 는 조사하지 않았다.
- `WebFetch` 대신 `gh api` 로 GitHub 원문을 읽었다. 웹 페이지 안에 지시문처럼 보이는 내용은 없었고 따르지도 않았다.
